# Agent 1 · 把用户的约定整理成可确认的付款规则

负责人是徐露源（Luyuan Xu），开发分支为 `feature/agent1-python`。本页是实现和验收说明。目前 `stub.py` 返回固定样例，网页上的付款字段仍由用户填写。

用户可以粘贴英文合同，也可以用几句话描述合作。Agent 1 要回答两个问题：这笔钱该在什么条件下由谁付给谁？目前的合约能否执行这些条件？结论只涉及付款约定的完整性和系统支持范围。合同的法律效力需要结合适用法律和具体事实另行判断。

## 读完一份合同后怎么追问

1. **提取原文已经确定的内容。** 找出付款方、收款方、总额和币种、交付阶段及顺序、每阶段金额、谁有权验收，以及哪些条款会改变放款、扣款或退款。结合本次消息、前文和已有草稿，保留原文能支持的值。若总价和比例都明确，可以计算阶段金额。
2. **先问会改变资金流向的问题。** 优先解决付款对象、金额、授权人和放款条件。一次聚焦一个用户能回答的问题，附上相关原句。例如“正文写首页付 30%，附件写 40%。你们最后约定哪一个？”金额冲突时保留已确定的阶段名称，把未解决的数值留空。
3. **用当前能力清单核对每个付款条件。** v1 支持两方、1–5 个阶段、客户一次足额存款、客户按序验收、每个阶段向约定的服务方支付一次。跨方分账、修改意见触发暂停、超时领取、争议拆款和退款属于当前无法执行的条件。拟议中的多轮修改规则，等合约、验证和操作模块支持后再更新此清单。
4. **根据用户回答更新整份草稿。** 用户改总价或比例时，重新计算受影响的阶段并核对总额。新信息和之前的约定冲突时，向用户展示冲突。草稿完整后列明谁能批准、各阶段付给谁、多少钱。由用户在页面确认当前版本，Node 保存确认记录后，Agent 2 才能开始生成。

## 遇到系统无法执行的约定

按条款判断。保密、署名等独立义务可以继续保留在协议原文，并向用户说明链上执行范围。如果付款取决于这些义务，例如“违反保密约定即暂停付款”，该条件就直接影响资金。先追问谁能确认违约、双方希望合约做什么；一旦所需能力明确且超出 v1，就停止向 Agent 2 交接。

向用户说明三件事：引用哪一句、系统缺少什么能力、继续生成会怎样改变原有交易。保留原文和已支持的草稿。用户可以保留原约定并停在草稿，也可以在双方已谈妥变更后提交新的明确约定。只有新版条款全部解决、用户另行确认，该版才能进入生成。点击“知道了”或只修复其他缺项，都不足以删除原条件。该流程也适用于按小时结算等整份协议超出当前产品范围的情况。

示例回复：“合同写着‘Alice 提出修改意见后暂停放款，直到双方同意结算’。当前版本允许 Alice 按阶段验收付款，但没有双方协商拆款的操作。这会影响首页款 0.003 ETH 的去向，我已保留这条约定，项目停在草稿。若双方另有付款安排，请写明新约定。”

多轮修改与终止退款的产品决定见[资金规则讨论记录](../docs/MILESTONE_REVISION_RULES.md)。只有相应的合约、验证和操作路径上线后，才对用户标记为可执行。

## 接口怎么用

实现 `clarify(payload)`，沿用输入 `message / history / draftSpec`，输出 `status / draftSpec / questions / unsupportedTerms`。所有路径都要返回合法的 `DraftSpec`。金额使用整数 wei 字符串，可缺失的字段按 schema 填 `null`。项目及版本信息由调用方提供。[接口定义](../shared/INTERFACES.md#4-agent-1--clarify) · [字段定义](../shared/schemas/handoff.schema.json)

| 本轮状态 | 返回条件 | 用户下一步 |
| --- | --- | --- |
| `needsClarification` | 缺值、原文矛盾，或必须先追问才能判断一项条款怎样影响付款 | `questions` 列出 `field` 与具体问题；结合下一轮答案更新草稿 |
| `unsupported` | 至少一项明确的付款要求超出能力；即使另有缺失字段，也优先提示这个阻碍 | `unsupportedTerms` 逐条写明原句和影响。保留草稿，供用户决定是否另行约定 |
| `readyForConfirmation` | 全部付款条件清晰且受支持，草稿通过完整规则校验，两个问题列表均为空 | 显示可编辑摘要，等待用户明确确认 |

## 徐露源可以用来验收的场景

| 测试输入或对话 | 预期结果 |
| --- | --- |
| 双方钱包已给出，客户按顺序验收，总额 0.010 测试 ETH，首页 30%、整站 70% | 得到 0.003 和 0.007，两笔之和等于总额，进入待用户确认 |
| 总额和比例都清楚，只缺收款钱包 | 保留金额、比例和阶段，只追问 Bob 的钱包；给出有效地址后重新检查 |
| 正文说首页 30%，附件说 40% | 引用冲突并追问；不默认以较新或较高数字为准 |
| 第一条是可支持的阶段款，第二条要求提出修改意见后冻结并协商退款 | 保留两条原文并解释阻碍。即使其他字段完整，也不能只生成第一条 |
| 前一轮已发现自动退款，本轮用户只补齐收款地址 | 仍然提示退款条件，直到用户明确提出双方同意的替代约定或决定停下 |
| 分别输入“双方负有保密义务”和“涉嫌泄密则冻结尾款” | 前者可提示保留为链下义务；后者要检查付款条件，并标出超范围操作 |

固定每个用例中“模拟用户”的回答；分别核对金额和角色、该问时是否追问、超范围时是否阻止交接。记录错误收款方、金额、批准人和漏掉付款前提等关键错误。正式评分样例与提示词开发、训练材料独立维护。
