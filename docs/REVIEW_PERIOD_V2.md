# 验收期与超时领取（v2 第一项，已实现）

2026-11-27 老板确认。属于[灵活合同架构规划](FLEXIBLE_CONTRACT_ARCHITECTURE.md)里的“超时领取”（T），按该文的版本与回退规则执行；v1 合约、接口和已部署项目不变。

## 规则

每个里程碑：

1. 服务方标记“已交付”，合约记录链上时间，验收期开始。
2. 验收期内客户可以批准（立即付款，同 v1），或要求修改（本次计时作废；服务方再次交付后重新计时）。
3. 验收期结束且客户没有回应，服务方发起领取，合约付款。合约不会自动执行，到期后由 Agent 3 提醒服务方领取。

验收天数写进生成的合约代码，部署后不能更改。仍按顺序逐期付款，每期只付一次。

## 已定的三项选择

| 问题 | 决定 |
| --- | --- |
| 合同没写验收期 | 默认不开启，也不追问；确认页提供一个可选开关（例如“客户 14 天不回应自动付款”） |
| 要求修改的次数 | 合同写了按合同（如“2 轮修改”）；没写不限次数，每次要求修改都重新计时 |
| 新规则的验证测试 | 先放在 `tests/v2/`，不改 `validation/`；由负责验证的组员接手后再迁移 |

合同写了“N 天内不提异议视为验收”时，Agent 1 直接读出 N；不能把“验收期 N 天”自行理解为沉默即验收。实现时起算点不再追问：一律从服务方标记交付起算，确认页写明“每次交付后 N 天”，用户不同意可以在对话里改。

## 用户体验

- 付款区每期显示状态：“已交付 · 还剩 6 天自动付款”“客户要求修改”。
- 本地演示中一个人同时扮演双方，所以不做切换，而是在每个按钮前写明角色：“Provider: mark as delivered”“Client: approve and pay”“Client: ask for changes”“Provider: claim”。
- 本地测试链提供“跳到验收期结束”（`POST /api/projects/:id/clock`），只在本地链显示，用来演示到期付款。

## 实施顺序

1. v2 接口草案、手写参考合约和合约测试。
2. `tests/v2/` 独立验证：到期前不能领取、到期后只能领一次、要求修改后不能领、乱序和重复付款被拒绝、强行转入的 ETH 不算存款。
3. Agent 2 生成带验收期的合约。
4. 后端、Agent 3 和网页：角色切换、交付／领取／修改操作、倒计时、时间快进。
5. Agent 1 识别验收期和确认页开关。样例用 Pelican 软件开发合同（10 天）和转租合同。

## 暂不解决

验收期只处理“客户不回应”，不处理“客户一直要求修改”。后者需要第三方仲裁，放到下一步。
